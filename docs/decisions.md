## 2026-09-02 — 画像ファイルの命名規則と、一括リネームをしない判断

### 背景

`images/setuplits/` の画像ファイル名には複数の形式が混在している。
#93 の画像が本番で 404 になっていた件（ファイル名の `.` が `,` になっていた打ち間違い）を
調査する過程で全体を棚卸ししたため、その結果をここに残す。

**混在は正常な状態であり、「変則名」でも「命名ミス」でもない。**
番組の運用形態が変わるのに合わせて命名も変わってきた、という履歴がそのまま残っているだけである。

### 実測した内訳（2026-09-02 時点）

全291回中、`image_file` を持つのは241件（残り50件は `null`）。
実ファイル存在チェックで**破損は0件**。

| 形式 | 件数 | 該当回 | 例 |
|---|---:|---|---|
| 新形式 `PUY年.回番号.拡張子` | 32 | #221〜#300 | `1995.300.png` / `1985.293.png` |
| 旧形式 `PUY年.放送年.MMDD.回番号3桁.拡張子` | 181 | #35〜#220 | `1986.2022.0705.093.png` |
| 旧形式・月日ゼロ埋めなし | 21 | #225〜#274 | `1987.2025.1.14.225.jpg` |
| アンダースコア区切り `PUY年_回番号.拡張子` | 6 | #261,264,265,275,277,279 | `1981_279.jpg` |
| ハイフン区切り `PUY年-回番号.拡張子` | 1 | #270 | `1999-270.png` |

移行は一点で切り替わったのではなく、以下の3つのゾーンに分かれている。

- **#220 以前** … 旧形式のみ
- **#221〜#279** … 移行期。新形式・旧形式・アンダースコア・ハイフンが混在
- **#280 以降** … 新形式のみ（#280 / #293 / #300）

### 旧形式が持っている情報

旧形式の `放送年.MMDD` 部分は**実際の放送日を保持している**。
データ側の `air_date` と突き合わせたところ **202件中200件が一致**した
（不一致は #98 と #187 の2件のみで、こちらはファイル名側の誤りと思われる）。
先頭の PUY 年は **202件中202件が一致**。

新形式の `PUY年.回番号` も **32件中32件**がデータと一致している。

つまりどちらの形式も規則的で、旧形式は放送日という**追加の情報を余分に持っている**。

### 決定：命名の一括統一は行わない

以下の理由により、旧形式を新形式へ揃える一括リネームは**やらない**。

1. **機能的な問題がない。** 全291回・241件の実ファイル存在チェックで破損0件。
   サイトは `image_file` の値でしか画像を読まないため、名前が揃っていなくても正しく動く。
2. **`setuplits.html`（566KB）の `image_file` 一括書き換えが必要になる。**
   これは #294 のデータ消失事故（`CLAUDE.md` 参照）と同種の操作であり、
   得られる利益に対してリスクが釣り合わない。
3. **旧形式は放送日情報を持つため、統一すると情報が失われる。**
   上記のとおり200件で放送日が裏取りできており、これは捨てるには惜しい。

### 再検討する条件

「画像を全面的に作り直す」など、どのみち全件に触れる大きな作業が発生する場合に限り、
そのついでに検討する。単独の目的として一括リネームに着手しないこと。

### 未解決（別件として棚上げ）

- 参照されていない追跡済み画像が15件ある。うち14件は #172〜#200 台のもので、
  `1983.2024.0604.193.jpg` と `.jfif` のように**同じ回の重複と思われる組**を含む。
  #93 とは別件として後日まとめて棚卸しする。

## 2026-09-02 — TOM★CAT の表記修正（生データ保持主義の例外）

### 何を直したか

**#293 no.3 のアーティスト名 `TOM☆CAT`（U+2606 白星）を `TOM★CAT`（U+2605 黒星）に修正した。**
対象は1件のみ。#293 は 2026-09-02 に追加した回で、追加時点の誤記をその日のうちに修正したもの。

### なぜ生データ保持主義の例外なのか

このリポジトリは原則として**表記の正規化を行わない**（`CLAUDE.md` および過去の運用方針）。
しかし今回は「表記ゆれ」ではなく「**明確な誤記**」であると判断した。根拠は以下。

1. **正式表記は ★（U+2605）である。**
2. **データ内の実績が 6 対 1 で ★ に偏っている。**
   修正前の TOM CAT レコードは全7件で、うち6件（#2 / #79 / #89 / #167 / #239 / #249）が
   すでに ★ を使っており、☆ は #293 の1件だけだった。
3. **`TOMCAT` / `トムキャット` といった他の表記ゆれは1件も存在しない。**
   揺れているのが星の種類だけであり、意図的な使い分けとは考えにくい。

#291 の「LAST GOOD-BYE」を正式表記に直した前例と同じ扱いである。

### 副作用：初登場バッジが1個減る

`normalizeForMatch` は ★(U+2605) と ☆(U+2606) を同一視しないため、
修正前の #293 no.3「ふられ気分でRock 'n' Roll」は #2（2020-10-05）の同曲と別曲と判定され、
**誤って初登場バッジが付いていた**。修正によりこれが解消される。

- 初登場バッジ総数：**2534 → 2533（−1）**
- 変化したのは #293 no.3 のみ（`[初登場]` → `初出=#2`）
- 他6件の TOM★CAT レコードの帰属は変化なし
- エピソード数291・全曲数5319は不変

つまりバッジの減少は損失ではなく、**誤記が生んでいた偽の初登場が消えた**という正常化である。

### 置換時の注意（次に同種の作業をする場合）

**☆(U+2606) の一括置換は絶対に行わないこと。** ☆ はこのデータ内で正式表記として現役である。

- `artist` フィールド：`ダンス☆マン`（#226）— 正式表記
- `title` フィールド：`涙がキラリ☆`（#28/#134）/ `情熱☆熱風せれなーで`（#61/#199）/
  `情熱☆熱風☽せれなーで`（#181）/ `リトル☆デイト`（#91）/ `キラメキ☆MMMBOP (MMMBop)`（#102）— いずれも正式表記

「artist フィールドのみを対象にする」という絞り方でも `ダンス☆マン` を巻き込むため不十分。
今回は `"artist":"TOM☆CAT"` という**完全一致文字列を1件だけ**置換し、
置換前後で ☆ の総数（9→8）・★ の総数（16→17）・ファイル長の不変をコードポイント単位で検証した。

## 2026-09-09 — 読み取り専用データ検証スクリプトの導入方針

### 背景

セットリスト更新時の大量削除、画像参照切れ、ランキング取得失敗による空データなどを、公開前にローカルで検出できる共通の確認手段がなかった。

### 決定

- `scripts/validate-data.mjs` はNode.jsの標準機能だけを使い、データやHTMLを変更しない読み取り専用ツールとする
- Set Up Listは `setuplits.html` 内の `SETUPLIST_DATA` を直接読み、別JSON・CSV・キャッシュなどの写しを作らない
- Git HEADとの比較は `git show HEAD:<path>` の出力をメモリ内で解析し、バックアップファイルを作らない
- 構造破損、必須項目欠落、画像参照切れなどはERROR、HEADからの件数減少やランキング年データの空配列は確認を促すWARNINGとする
- WARNINGだけなら終了コード0、ERRORがあれば非0とし、将来の自動検証でも利用できる形式を維持する
- 異常検出の自己テストは合成データをメモリ内で処理し、本番データをテスト用に変更・複製しない

この段階ではGitHub Actionsや自動修復を導入せず、`npm run validate` による手動確認だけを提供する。

## 2026-09-09 — GitHub Actionsでデータ検証を自動実行する判断

### 背景

前項の読み取り専用データ検証をローカルだけでなく、`main` へのpushと`main`向けpull requestでも自動実行する第2段階へ進めた。

### 決定

- `.github/workflows/validate.yml` は検証専用とし、デプロイ、データ更新、自動修復、commit、pushを行わない
- workflowの権限は `contents: read` だけとし、secretsやwrite権限を使用しない
- Node.js 20.19.0で `npm ci` と既存の `npm run validate` を実行する
- GitHub Pagesの公開設定や既存デプロイ方法には触れない
- triggerは `main` へのpushと`main`向けpull requestだけに限定する

GitHub Actionsではcheckout後の作業ツリーとHEADが同じ内容になるため、validatorのHEAD件数比較は主にローカル更新時の確認機能となる。CIでは構造破損、必須項目欠落、画像参照切れなど、現在のcheckout内容に対する検証を担う。base branchとの件数比較は、比較元の取得とvalidatorの入力設計が必要になるため、この最小構成には含めない。

- grapheme cluster分割には利用可能なら `Intl.Segmenter` を使う。非対応環境ではUnicodeコードポイント走査による簡易fallbackを使い、結合文字、半角カナ濁点・半濁点、variation selector、emoji modifier、ZWJ連結、regional indicatorの2個組、主要なIndic virama後の文字を直前clusterへ含める。主要対象ブラウザでは `Intl.Segmenter` を優先し、fallbackでもサロゲートペアとZWJ連結を分断しない。追加ライブラリは使用しない
- 動的な元文字列断片は通常部・強調部とも既存の `esc()` でHTMLエスケープし、強調部だけを固定HTMLの `<mark class="chart-search-highlight">` で囲む。検索語はHTMLへ出力せず、正規表現にも組み込まない
- 対象は `year-end-chart.html` の検索結果にある曲名・アーティスト名だけとし、元データ、表示表記、検索判定、年代絞り込み、並び順、件数、通常ランキング、`data.json` は変更しない
